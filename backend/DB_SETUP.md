# Setting up the OBA database (schema + data)

You were already sent `data/company.json`. **Ignore it for this step** — there is no
script that loads a database from that JSON, and you don't need one. `company.json` is a
one-way *export* of the database (generated by `tools/export-company.js`); the database
itself is built from the SQL files in this package. Running the steps below puts the
exact same data into your database that `company.json` is a snapshot of — confirmed by
regenerating it from these files and diffing against the copy you were sent (identical,
aside from one unrelated stale field unrelated to this handoff).

So: **do not try to import the JSON.** Just run the migrations below — schema and data
both land in one step.

## What you were given

```
schema.sql
run_migrations.js
sql/
  01_schema_migration.sql
  02_seed_data.sql
  03_fizza_modules_schema.sql
  04_fizza_modules_seed.sql
  05_foreign_keys.sql
  06_missing_columns.sql
  07_intent_accountability.sql
  08_execution_mode_set_by.sql
  09_ai_platforms_vendor.sql
  10_ai_platforms_knowledge_gaps.sql
  11_foreign_key_indexes.sql
  12_consolidate_single_tenant.sql
  13_drop_frozen_aggregates.sql
  14_authored_entities.sql
  auth_schema.sql
```

Put all of it inside your project's `backend/` folder, at exactly these paths —
`schema.sql` and `run_migrations.js` directly in `backend/`, everything else inside
`backend/sql/`. The runner finds files relative to its own location, so the layout has
to match exactly.

## 0. Requirements

- Node.js 22+
- `pg` and `dotenv` npm packages (already in this repo's `backend/package.json`; if
  yours doesn't have them: `npm install pg dotenv`)
- A **Postgres database with nothing in it** — see the warning below before pointing
  this at anything that isn't empty.

## ⚠ This must be a brand-new, empty database

`01_schema_migration.sql` starts with `DROP TABLE IF EXISTS` across 42 tables. On a
truly empty database that statement does nothing (there's nothing to drop) and is
harmless. **If you point this at a database that already has tables or data in it —
yours or anyone else's — that data is deleted, permanently, with no confirmation
prompt.** Create a fresh Supabase project (or fresh Postgres instance) specifically
for this before continuing. Do not reuse an existing one "just to try it."

## 1. Create a database

Easiest path: [supabase.com](https://supabase.com) → New Project (free tier is fine).
Wait for it to finish provisioning.

## 2. Get the connection string

In the Supabase dashboard: **Project Settings → Database → Connection string → URI**.

Copy the **pooler** connection string — it looks like:

```
postgresql://postgres.<your-ref>:<password>@aws-0-<region>.pooler.supabase.com:5432/postgres
```

**Do not use** the other connection string shown there
(`db.<your-ref>.supabase.co`) — that host is IPv6-only and will fail to resolve
(`ENOTFOUND` / `ETIMEDOUT`) on most laptops and on GitHub Actions runners. If your
migration hangs or fails to connect, this is the first thing to check.

## 3. Create `backend/.env`

In your `backend/` folder, create a file named exactly `.env` containing:

```
DATABASE_URL=postgresql://postgres.<your-ref>:<password>@aws-0-<region>.pooler.supabase.com:5432/postgres
```

Replace `<your-ref>`, `<password>`, `<region>` with the real values from step 2.
`run_migrations.js` reads only this one variable. (Your app itself will separately
need `SUPABASE_URL` / `SUPABASE_KEY` from the same project's **Project Settings → API**
page, but those aren't used by the migration step — just don't skip setting them up
before you try to run the app.)

## 4. Preview — changes nothing

From inside `backend/`:

```bash
node run_migrations.js --dry-run
```

Expected output: a list of 16 pending files (`schema.sql` + everything in `sql/`, in
the order shown above). If you get a connection error instead, fix step 2/3 before
continuing — nothing has run yet, so there's nothing to undo.

## 5. Apply — this is the step that creates the schema AND loads the data

```bash
node run_migrations.js
```

This runs `schema.sql`, then every file in `sql/` in filename order, each inside its
own transaction. As each file finishes it prints `OK`; if one fails it prints `FAILED`,
rolls back that one file only, and stops — nothing partial is left committed, and
nothing after the failing file has run. You'd fix the error and re-run; already-applied
files are skipped automatically (see step 6).

`02_seed_data.sql` and `04_fizza_modules_seed.sql` are what actually insert the data —
40 employees, 15 agents, 12 AI tools, workflows, dependencies, collaborations, and so
on. There is no separate "seed" command to run; it happens as part of this same call.

## 6. Confirm it worked

```bash
node run_migrations.js --dry-run
```

should now print `Nothing to apply — all migrations recorded.` That's your
confirmation every file applied and is recorded in the `schema_migrations` table it
created. This makes the runner idempotent: running `node run_migrations.js` again
later (e.g. after you add a `15_...sql` file of your own) only applies what's new.

Then check the data landed, either via the Supabase Table Editor (open the `employees`
table, expect 40 rows) or with `psql`:

```bash
psql "$DATABASE_URL" -c "select count(*) from employees;"
```

Expect `40`.

## Rules for afterwards (don't skip these)

- **Never run any of these `.sql` files by hand** — not in the Supabase SQL editor, not
  with `psql`, not "just to check one table." `run_migrations.js` is the only supported
  way to apply them. Running `01_schema_migration.sql` directly re-triggers its
  `DROP TABLE` across 42 tables with no ledger to stop it.
- **Never delete rows from the `schema_migrations` table.** That table is the ledger
  that makes re-running the migration command safe — removing a row makes its file
  eligible to run again, and for `01_schema_migration.sql` that means the DROP.
- **Never run `node run_migrations.js --baseline`** on this database. It marks files as
  applied *without running them* — only useful for adopting an already-hand-built
  database, which doesn't apply here since you're starting empty.
- If you add your own schema changes later, add a new numbered file
  (`15_whatever.sql`) to `sql/` rather than editing an existing one — edited files
  that are already in the ledger will never re-run, so your team would silently miss
  the change.
